# 03 · 数据格式说明

这篇讲清楚三件事：**云端 Gist 里到底存了什么**、**本机存了哪些东西**、**每个字段是什么意思**。

---

## 1. 云端 Gist 里有什么

第一次同步时，扩展会在你的 GitHub 账号下创建一个**私有 Gist**，里面有两个文件：

```
cloudbookmark.json   ← 全部书签数据（主文件）
README.md            ← 一段说明文字，方便你以后打开时知道这是什么
```

Gist 的**描述**被固定写成 `cloudbookmark-sync`，
扩展就是靠"文件里有没有 `cloudbookmark.json`"以及这个描述来认出"自己的 Gist"。

### cloudbookmark.json 的样子

```json
{
  "kind": "cloudbookmark",
  "schema": 1,
  "revision": "a1b2c3d4e5f60718",
  "generatedAt": "2026-06-03T12:00:00.000Z",
  "deviceId": "dev-k7Fq2mXp9vLd",
  "deviceName": "Chrome on Windows",
  "count": 3,
  "entries": [
    {"uid":"root:0","parentUid":"","index":0,"kind":"folder","title":"书签栏","url":null,"createdAt":"...","updatedAt":"..."},
    {"uid":"root:1","parentUid":"","index":1,"kind":"folder","title":"其他书签","url":null,"createdAt":"...","updatedAt":"..."},
    {"uid":"k7Fq2mXp9vLdR3sT","parentUid":"root:0","index":0,"kind":"bookmark","title":"GitHub","url":"https://github.com","createdAt":"...","updatedAt":"..."}
  ]
}
```

**每条记录占一行**是刻意设计的：用普通编辑器打开也能看清，
用 GitHub 的 diff 看改动也很直观（缩进太深的话体积会膨胀好几倍）。

### 顶层字段

| 字段 | 含义 |
|------|------|
| `kind` | 固定 `"cloudbookmark"`，用来识别"这是我们的文件" |
| `schema` | 格式版本号。以后结构要改时靠它做迁移 |
| `revision` | **内容指纹**。只由"影响同步的字段"算出来，时间戳变化不会让它变 |
| `generatedAt` | 这份文件是什么时候生成的（就是这个设备上次同步的时间） |
| `deviceId` / `deviceName` | 最后写这份文件的是哪台设备。界面上显示"云端最后来自"就用它 |
| `count` | 记录条数，方便肉眼核对 |
| `entries` | 所有书签和文件夹，**扁平数组**（层级关系靠 `parentUid` 表达） |

### 每条记录（Entry）的字段

| 字段 | 类型 | 含义 |
|------|------|------|
| `uid` | 字符串 | **永久身份**。跨设备、跨浏览器都是同一个值 |
| `parentUid` | 字符串 | 父节点的 uid。空字符串 `""` 表示"它本身是一个根目录" |
| `index` | 数字 | 在同一个父节点下排第几（从 0 开始） |
| `kind` | `"folder"` 或 `"bookmark"` | 是文件夹还是书签 |
| `title` | 字符串 | 标题。可能为空字符串 |
| `url` | 字符串或 `null` | 书签的网址；文件夹固定是 `null` |
| `createdAt` | ISO 时间 | 创建时间，主要用于展示 |
| `updatedAt` | ISO 时间 | 最后修改时间（**近似值**，见下） |

> **为什么层级是"扁平 + parentUid"而不是嵌套的 `children`？**
> 因为同步要**逐条**比较、逐条合并。扁平结构里"查一条记录"是 O(1)，
> 嵌套结构每层都要递归。需要树形展示时，用 `buildTree()`
> （`src/core/entries.ts`）现场组装即可。

> **`updatedAt` 为什么是"近似值"？**
> 因为 `chrome.bookmarks` 不提供"这条书签最后一次改标题是什么时候"。
> 我们能拿到的是"文件夹内容被修改的时间"。所以这个字段只在两种时候是准的：
> 我们自己写入的时候（打上当前时间），以及从别的设备同步过来的时候。
> 它只用于展示，**不参与任何合并判断**——这一点很重要，否则每次同步都会
> 因为时间戳变化而误判成"用户改了东西"。

## 2. 兼容旧版本格式

如果你之前用过 v1/v2，Gist 里可能是旧的文件名 `bookmarks.json`，长这样：

```json
{
  "version": 3,
  "roots": {
    "bookmark_bar": { "id": "1", "title": "书签栏", "children": [ ... ] },
    "other": { ... },
    "mobile": { ... }
  }
}
```

扩展读取时的顺序是：

1. 先找 `cloudbookmark.json`（新格式）
2. 找不到再找 `bookmarks.json`（旧格式）→ 自动转换成新格式，并给出一条提示
3. 转换完之后，**下一次上传时会顺手把旧文件删掉**（PATCH 时把文件内容设为 `null`
   就是删除文件的意思），保持 Gist 干净

旧格式里的 id（形如 `bm_5`）是**设备本地 id**，不能当身份用，
所以迁移时会给每条记录分配新的随机 uid。这也是为什么迁移之后，
第一次同步需要靠"按网址配对"来和本机书签对上号（见 02 文档第 5 节）。

## 3. 本机存了哪些东西

### 3.1 `chrome.storage.local`（小数据，界面要实时看）

只有一个"键值对仓库"，键名是固定的：

| 键 | 内容 | 为什么放这里 |
|----|------|-------------|
| `settings` | 设置（自动同步开关、间隔、冲突策略…） | 小，而且界面要立刻看到变化 |
| `syncState` | 同步状态（状态、阶段、上次时间、冲突数…） | 界面订阅它的变化来自动刷新 |
| `deviceId` | 设备 id，形如 `dev-k7Fq2mXp9vLd` | 生成一次就不再变，Token 加密也用它 |
| `gistId` | 当前使用的 Gist 的 id | 避免每次都去列表里翻找 |
| `tokenBlob` | **加密后**的 Token：`{ iv, data }` | 明文 Token 只存在内存里 |
| `accountLogin` | 上次验证成功的 GitHub 用户名 | 只用于在界面上显示 `@用户名` |

### 3.2 IndexedDB（大数据）

数据库名 `cloudbookmark`，有三个"对象仓库"（可以理解成三张表）：

**`blobs`** —— 存放大的对象，用固定的键名区分：

| 键 | 内容 | 用途 |
|----|------|------|
| `snapshot:base` | 上次同步完成时的完整快照 | 三方合并的"第三份数据"，**最关键的本地数据** |
| `uidmap` | `浏览器节点id → { uid, synthetic, updatedAt }` | 让同一本书签永远认得自己 |
| `pending:sync` | 待用户处理的冲突（合并结果 + 冲突列表 + 相关快照） | 冲突界面读它 |
| `backup:local` | 覆盖本地之前的本地快照 | "回滚"用 |
| `backup:remote` | 覆盖云端之前的云端快照 | "回滚"用 |

**`changelog`** —— 书签变更记录（你在浏览器里手动改书签的流水）

**`synclog`** —— 同步历史（每次同步的时间、模式、改动量、是否成功）

> 升级到 v3 时，旧版本用过的 `bookmarks` / `tombstones` / `syncMeta` /
> `changeRecords` 四个仓库会在数据库升级时被**自动删除**，把空间还回来。
> 代码见 `src/platform/blob-store.ts` 的 `upgrade` 回调。

## 4. 导出文件 = 云端格式

"数据"标签页导出的 JSON 和云端 `cloudbookmark.json` **格式完全一样**。
这么设计有两个好处：

1. 你可以把导出的文件直接复制粘贴到 Gist 里当备份恢复
2. 只有一套解析代码，不会出现"导出能读、云端读不了"这种事

导出文件名形如 `cloudbookmark-2026-06-03-12-00-00.json`。

导入时有两个选项：

| 选项 | 行为 |
|------|------|
| **合并进现有书签**（默认） | 把文件当成"另一边的数据"做一次三方合并，两边都保留 |
| **替换现有书签** | 直接用文件内容替换本地书签，原来的会消失 |

**导入只改本地，不碰云端。** 导入后要自己点一次"同步"才会推到云端。

---

## 5. 数据大小与限制

| 限制 | 数值 | 应对 |
|------|------|------|
| Gist 单个文件 | GitHub 对超过约 1MB 的文件会在 API 返回里**截断内容** | 扩展检测到 `truncated` 标记时会改从 `raw_url` 取全文，所以能正常处理 |
| 实际体积 | 一条书签约 200 字节，一万条书签约 2MB | 超过限制时上传会被 GitHub 拒绝，界面会提示"书签数据太大，建议先清理重复书签" |
| GitHub 接口次数 | 认证用户 5000 次/小时 | 内容没变就不上传；自动同步有防抖和最小间隔 |

想自己估算体积：打开 Gist 看 `cloudbookmark.json` 的字节数即可。

---

## 6. 手动改云端文件会怎样？

**可以看，但不要改。** 如果 JSON 语法错了，同步时会提示
"远端文件不是合法的 JSON，可能被手工改坏了"，然后停下来，不会破坏你的本地书签。

如果你改的是内容（比如把某个标题改了），会被当成"云端的一次修改"正常参与合并——
这正是"数据在你自己手里"的体现。但请务必保持 JSON 合法。

想安全地手工编辑的话：先"导出 JSON"改好，再用"导入 → 替换"还原。
