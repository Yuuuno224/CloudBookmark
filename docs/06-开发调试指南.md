# 06 · 开发调试指南

## 1. 环境准备

```bash
node -v        # 需要 18 以上，推荐 20/22
npm install    # 安装依赖
```

依赖只有三个是"运行时"的，其余都是编译期工具：

| 依赖 | 作用 |
|------|------|
| `solid-js` | 界面框架（很小，压缩后几十 KB） |
| `idb` | 让 IndexedDB 用起来像普通函数 |
| `@crxjs/vite-plugin` | 让 Vite 能编译浏览器扩展（会自动改写 manifest） |

## 2. 常用命令

```bash
npm run typecheck   # 只做类型检查，不产出文件。改完代码先跑这个，几秒出结果
npm test            # 跑单元测试 + 端到端仿真（102 个用例，约 1 秒）
npm run test:watch  # 监听模式，改代码自动重跑
npm run build       # 类型检查 + 生产构建，产出到 dist/
npm run dev         # 开发模式（带热更新），详见第 4 节
```

> 早先版本还有一个 `npm run lint`，但项目里从来没有 ESLint 配置文件，
> 这条命令一直是坏的。新版本把它删掉了——与其留一条必然报错的命令，
> 不如老老实实用 `typecheck` + `test`。
> 想加代码检查的话：`npm i -D eslint typescript-eslint`
> 然后建一个 `eslint.config.js` 即可。

### 关于 package-lock.json：这个仓库故意不提交它

这不是偷懒，是被坑过之后的选择。

Vite 8 内部用 `rolldown`，PostCSS/Tailwind 用 `lightningcss`，
这两个包都会按平台安装**不同的原生二进制**：

```
@rolldown/binding-win32-x64-msvc     ← Windows
@rolldown/binding-linux-x64-gnu      ← Linux
@rolldown/binding-darwin-arm64       ← macOS (Apple Silicon)
lightningcss-win32-x64-msvc / lightningcss-linux-x64-gnu / …
```

而 `package-lock.json` **只记录生成它的那台机器上的那一个**。
于是「在 Windows 上生成的锁文件」会让 Linux 上的 CI 装不到 Linux 版二进制，
`vitest` / `vite` 一启动就崩，报的错还特别难懂：

```
Cannot find module '../rolldown-binding.linux-x64-gnu.node'
```

**不提交锁文件时**，每台机器（以及 CI）的 `npm install` 都会各自解析出
自己平台需要的原生包，这是最省事的做法。

顺带两个连带影响，改工作流时要注意：

- **`actions/setup-node` 不能加 `cache: npm`**。缓存功能要求仓库里有锁文件，
  没有锁文件会直接报错。所以 `ci.yml` / `release.yml` 里都没有开缓存。
- CI 里多了一步「环境与原生模块检查」，会显式地 `import('rolldown')` 和
  `import('lightningcss')`。这样万一以后又装错平台，报错信息是清楚的，
  而不是让你对着 `MODULE_NOT_FOUND` 猜。

**想要可复现安装怎么办？** 在 **Linux** 机器上跑一次 `npm install`
生成锁文件再提交——那一次的锁文件会同时记录所有平台的原生包
（npm 从 registry 解析时会带上 `os`/`cpu` 信息，各平台按需取用）。
同时记得把工作流里的 `cache: npm` 加回来。

## 3. 把扩展装进浏览器

```bash
npm run build
```

然后：

1. 打开 `chrome://extensions/`（Edge 是 `edge://extensions/`）
2. 右上角打开 **开发者模式**
3. 点 **加载已解压的扩展程序**
4. 选择项目里的 **`dist` 目录**（不是项目根目录！）
5. 建议把 CloudBookmark 固定到工具栏，方便看状态徽章

改完代码要重新构建，然后到扩展页面点一下 CloudBookmark 卡片上的
**刷新按钮**（圆圈箭头）才会生效。

## 4. 开发模式（带热更新）

```bash
npm run dev
```

CRXJS 会启动一个 Vite 开发服务器（默认 `http://localhost:5173`）。
它会在 `dist` 里生成一份"指向开发服务器"的扩展，改界面代码时浏览器会自动刷新。

**但有两件事必须记住：**

1. **Service Worker 的改动不会自动生效。**
   改 `src/background/**` 之后，要去 `chrome://extensions/` 点刷新按钮，
   或者干脆关掉扩展开关再打开。
2. **改了 `src/manifest.ts` 之后必须重启 `npm run dev`**，
   因为清单只在启动时生成一次。

## 5. 看日志：这是最重要的调试手段

扩展分两个运行环境，**日志在两个不同的地方**：

### 5.1 后台（Service Worker）的日志

`chrome://extensions/` → CloudBookmark 卡片 → 点 **「Service Worker」**
（中文界面是「服务工作线程」）→ 会弹出一个 DevTools 窗口。

所有同步相关的日志都在这里。同步失败的原因、GitHub 返回的错误都会打在这里。

> ⚠ Service Worker 会被浏览器休眠，休眠时 DevTools 会显示 "inactive"。
> 这时点一下扩展图标（唤醒它），日志就继续了。
> 调试时可以在 DevTools 的 Sources 面板里什么都不做，
> 但更可靠的办法是临时把自动同步间隔调短，让它自己反复醒过来。

### 5.2 界面的日志

- **弹窗**：在弹窗上右键 → **检查**
- **设置页**：在设置页上右键 → **检查**（就是一个普通标签页）

### 5.3 看本机存了什么

在后台的 DevTools 里：

- **Application → Storage → Extension Storage** → 能看到 `settings`、`syncState` 等
- **Application → Storage → IndexedDB → cloudbookmark** → 能看到
  `snapshots`（base、备份）、`uidmap`、日志

这是排查"状态不对"最快的方法。想看 base 快照的完整内容，
在 Console 里执行：

```js
const db = await new Promise((res, rej) => {
  const r = indexedDB.open('cloudbookmark');
  r.onsuccess = () => res(r.result);
  r.onerror = () => rej(r.error);
});
const tx = db.transaction('blobs', 'readonly');
const all = await new Promise((res) => {
  const req = tx.objectStore('blobs').getAll();
  req.onsuccess = () => res(req.result);
});
console.table(all.map((r) => ({ key: r.key, savedAt: r.savedAt })));
```

## 6. 代码里的日志约定

| 前缀 | 含义 |
|------|------|
| `[CloudBookmark] ...` | 扩展自己的日志 |
| `console.warn` | 自动同步失败之类"不打扰用户但需要注意"的情况 |
| `console.error` | 真的出错了 |

**永远不要把 Token 打进日志。** 项目里所有涉及 Token 的地方都刻意没有 `console.log`。

## 7. 跑测试

```bash
npm test
```

会跑 5 个测试文件、102 个用例，一秒左右出结果。它们覆盖的是：

| 文件 | 覆盖内容 |
|------|---------|
| `tests/core.merge.test.ts` | 三方合并的每个分支：增删改、字段级合并、冲突、排序、脏数据 |
| `tests/core.snapshot.test.ts` | 序列化往返、内容指纹、旧格式迁移、首次配对、重复检测 |
| `tests/core.entries.test.ts` | 孤儿/环的修复、排序编号、组装树 |
| `tests/platform.apply.test.ts` | 写回浏览器：创建、更新、移动、删除、排序、替身根目录、身份改名 |
| `tests/e2e.sync.test.ts` | **两台假设备 + 一个假 Gist 的完整同步仿真** |

最后一个是重点。它不需要浏览器，因为它用的是内存版的"假浏览器"
（`tests/fakes/fake-browser.ts`）和"假 Gist"（`tests/fakes/fake-remote.ts`）。
想验证一个新场景（比如"三台设备同时改同一本书签"），
照着 `e2e.sync.test.ts` 里的写法加一个 `it(...)` 就行。

### 加一个测试的套路

```ts
it('我的场景', async () => {
  const a = makeDevice('设备A', 'dev-a');
  const b = makeDevice('设备B', 'dev-b');

  a.browser.addBookmark(a.browser.barId, '标题', 'https://example.com');
  await a.service.run('merge');   // A 同步
  await b.service.run('merge');   // B 同步

  expect(b.browser.countByUrl('https://example.com')).toBe(1);
});
```

`makeDevice` / `FakeBrowser` 提供的方法（见 `tests/fakes/fake-browser.ts`）：

| 方法 | 作用 |
|------|------|
| `addBookmark(parentId, title, url)` | 加一条书签，返回它的浏览器 id |
| `addFolder(parentId, title)` | 加一个文件夹 |
| `titlesOf(parentId)` | 某个文件夹下的标题顺序 |
| `countByUrl(url)` | 这个网址当前有几条 |
| `findByUrl(url)` | 找到节点（可以 `.id`、`.title` 看详情） |
| `path('书签栏', '开发')` | 按路径取文件夹 id |

## 8. 常见开发坑（踩过一次就够了）

### 加了监听器但"时好时坏"

**原因**：监听器写在 `async function init()` 里了。
MV3 的 Service Worker 会被休眠，醒来时重新执行入口文件，
如果监听器注册在异步函数里，这次就没装上。

**正确做法**：所有 `chrome.xxx.addListener` 都写在 `src/background/index.ts`
的**模块顶层**。

### 同步之后变更记录被刷屏

**原因**：我们自己写书签也会触发 `chrome.bookmarks.onCreated`。

**正确做法**：写入前后调用 `changeTracker.suppressFor(毫秒)`。
`src/background/handlers.ts` 里有个 `withoutChangeNoise()` 包装函数就是这个用途。

### 书签"删了又回来" / 出现重复

**原因**：uid 没保存，或者身份表被清掉了。每次读本地时新节点会现场生成 uid，
**必须立刻保存**（`service.readLocal()` 里做了这件事），
否则下次读身份又变了，就会认成两条不同的记录。

### 改了 manifest 不生效

必须重新构建（或重启 `npm run dev`），然后在扩展页面点刷新按钮。

### 上传被 GitHub 拒绝（422）

书签数据太大，超过了 Gist 单文件限制。用"数据"标签页清理重复书签，
或者减少同步的根目录。

### `npm run build` 报 `spawn EPERM`

这是**运行环境把子进程挡住了**，不是项目的问题。
Vite 在 Windows 上会执行一次 `net use` 来探测网络驱动器，被安全策略拦了。
换一个正常的命令行环境，或者在有完整权限的终端里跑就行。

## 9. 发布流程

项目自带 GitHub Actions（`.github/workflows/`）：

- `ci.yml`：push 到 main 或提 PR 时跑类型检查 + 构建 + 测试，产物上传为 artifact
- `release.yml`：推一个 `v3.0.0` 这样的 tag 时，自动打包 `dist` 成 zip 并创建 Release

```bash
# 手动发版
npm version 3.1.0 --no-git-tag-version   # 更新 package.json 里的版本号
git commit -am "chore: release 3.1.0"
git tag v3.1.0
git push && git push --tags
```

版本号会在构建时自动写进 `manifest.json`（`src/manifest.ts` 里直接引用了
`package.json` 的 `version`），所以只需要改一个地方。
