# 08 · 本次重构改了什么

这篇是"旧版本哪里坏了、新版本分别怎么修的"的完整清单。
旧代码已经不在仓库里了，但如果你想知道某个行为为什么变了，可以查这里。
（旧版设计文档归档在 `docs/archive/旧版技术方案-v1.md`。）

---

## 一、致命问题（会丢数据或让功能完全失效）

### 1. 用浏览器本地 id 当书签身份 → 跨设备认不出、删不掉

**旧做法**：把书签的身份写成 `bm_<浏览器id>`，而这个 id 是**本机临时 id**。

**后果**：

- 同一本书签在 A 设备是 `bm_5`、在 B 设备是 `bm_17`，合并时被当成两条 → 满屏重复
- 更糟的是"删除"：代码要用 `toBrowserId()` 把 uid 换回浏览器 id 才能删，
  而这个映射表只存在**内存变量**里。Service Worker 一休眠就没了，
  于是 `chrome.bookmarks.remove('bm_5')` 直接抛错，被 `catch {}` 静默吞掉
  → **删除永远不生效，但用户看不到任何提示**

**新做法**：见 `src/platform/uid-map.ts`。

- 每条记录有一个跨设备稳定的随机 `uid`（16 位、62 进制）
- `浏览器id ↔ uid` 的对应关系持久化在 IndexedDB 里，读一次就立刻保存
- 根目录用**位置推导**的固定 uid（`root:0`、`root:1`），
  这样 Chrome 和 Edge 能对上号

### 2. 删除根本不会同步（墓碑机制从未生效）

**旧做法**：设计文档里写了"删除时写一条墓碑（tombstone）到 `deleted.json`"，
代码里也有读取和应用墓碑的逻辑。但**从来没有地方写入过墓碑**——
删除只被记进"变更记录"（那是给用户看的日志），没有传给同步引擎。

**后果**：你在一台设备上删书签，另一台设备上它永远还在。而且因为问题 1，
连"本地删除"这件事都传不出去。

**新做法**：不需要墓碑了。有了 base 快照之后，
"云端没有 + base 里有 + 本地没动" = 云端删了它，天然可传播。
（原理见 [02-同步原理](02-同步原理-三方合并.md) 第 6 节。）
少了一套机制，反而更可靠。

### 3. Service Worker 醒来后监听器没注册

**旧做法**：书签变更监听器写在 `async function init()` 里，
而 `init()` 只在 `onInstalled` / `onStartup` 时调用，还要求"已经配了 Token"。

**后果**：MV3 的 Service Worker 会被随时休眠、醒来后重新执行入口文件。
醒来时监听器没装上 → **变更记录时有时无、自动同步随机失效**。
这种"偶发 bug"最难查。

**新做法**：所有 `chrome.xxx.addListener` 都写在 `src/background/index.ts`
的**模块顶层**，不依赖任何异步初始化。

### 4. 冲突时把"上次同步版本"记成了错误的值

**旧做法**：检测到冲突后，代码把 `lastSyncVersion` 设成了"远端当前版本"，
但**本地实际什么都没应用**。

**后果**：扩展以为"已经同步过了"，本地和 base 从此对不上，
之后的每次同步都在错误的基准上算，越错越远。

**新做法**：冲突时**绝不碰 base**，只把合并结果和冲突列表存进
`pending:sync`，状态标成"等待处理"。只有真正应用完成后才更新 base。

### 5. URL 去重会静默丢弃书签

**旧做法**：合并时维护一个"已出现过的 URL 集合"，
遇到重复 URL 的记录**直接 `return false` 丢掉**。

**后果**：你在两个文件夹里各放了一条 `github.com`（完全合法），
同步之后**其中一条无声无息消失了**。用户永远不知道发生了什么。

**新做法**：

- 合并阶段**不做 URL 去重**，重复 URL 一律保留（浏览器本来就允许）
- 只有在**第一次同步**、"两边都只出现一次"时，才用 URL 做**身份配对**
  （目的是避免新设备产生重复，而不是删东西）
- 想清理重复？「数据」标签页有专门工具，会先列出来给你看，再让你确认

### 6. 判断"内容是否相同"时包含了所在文件夹

**旧做法**：`isSameContent()` 比较 `title + url + type + parentId`。

**后果**：只要一方移动了书签，就会被判成"内容变了"。
如果另一端也改过（哪怕只改了标题），就会变成冲突；本该自动合并的变成要人工处理。

**新做法**：拆成两个函数（`src/core/entries.ts`）：

- `contentEquals()` 包含 `parentUid`，用于合并判断（移动必须被感知）
- `bodyEquals()` 只比 `kind/title/url`，用于把"更新"和"移动"分开统计

## 二、功能性缺陷

| # | 旧问题 | 新做法 |
|---|--------|--------|
| 7 | 声明了 `alarms` 权限却从未使用，**没有定时同步** | `src/background/scheduler.ts`：定时同步（默认 15 分钟，可配 5/15/30/60/180） |
| 8 | 没有"变更后自动同步" | 书签变化后 3 秒防抖自动同步，可在设置里关 |
| 9 | 上传前不检查云端是否有新内容，**直接覆盖** | `needsConfirm: 'overwrite-remote'`：云端有未合并内容时先要你确认 |
| 10 | 下载前不提示本地改动会丢，**直接覆盖** | `needsConfirm: 'overwrite-local'`：先确认 |
| 11 | 覆盖操作**没有备份**，覆盖了就回不来 | 每次覆盖前自动备份本地和云端快照，「数据」页可一键回滚 |
| 12 | `findSyncGist()` 只查**前 100 个** Gist | 翻最多 3 页（300 个），并优先按"有没有 `cloudbookmark.json`"来认，比按描述文字匹配可靠 |
| 13 | 书签列表加载失败：`new URL(node.url).hostname` 遇到非法 URL 会抛异常，被外层 catch 吞掉 → **整个列表空白** | 列表视图重做，解析失败时回退到原始网址 |
| 14 | 书签列表只是只读平铺，漏掉根文件夹本身，没有搜索 | 改为在「冲突」和「数据」页提供**结构化、有上下文**的视图，而不是一个没用的只读列表 |
| 15 | 移动操作的变更记录 `title` 是空字符串 → 列表里显示裸 id | 记录时带上标题和网址 |
| 16 | 冲突界面在 360px 的弹窗里挤成一团 | 冲突处理搬到独立设置页，「冲突」标签用表格并排对比 |
| 17 | `SyncStatus` 的同步模式存在组件局部状态里，切标签就重置 | 设置持久化在 `chrome.storage.local` |
| 18 | 界面出错时 `catch {}` 吞掉所有异常，**用户看不到失败原因** | `sendRequest` 失败会抛 `AppError`，`useAction()` 统一显示错误，且错误码可翻译成中文提示 |

| 20 | 冲突只可能在合并时产生，但界面文案说"下载时检测到冲突" | 明确区分四种操作：合并同步 / 上传覆盖 / 下载覆盖 / 导入 |
| 21 | 没有"导出/导入 JSON"、"清理重复"、"查看统计" | 「数据」标签页全都有 |
| 22 | 没有同步历史，出错了不知道该看什么 | 「历史」标签页：每次同步的时间、模式、改动量、成败 |
| 23 | 没有状态徽章，必须打开弹窗才知道有没有问题 | 图标徽章：`…` 同步中 / 数字 冲突数 / `!` 出错 |
| 24 | 换 Gist、忘记 Gist 都做不到 | 设置页可以查看 Gist id、打开 Gist、忘记当前 Gist |

## 三、正确性与健壮性

| # | 旧问题 | 新做法 |
|---|--------|--------|
| 25 | `rebuildTree()` 会**静默丢掉**父节点不存在的记录 | `repairHierarchy()`：孤儿挂到「其他书签」并给出提示，**绝不丢数据** |
| 26 | 文件夹互相嵌套成环时，树组装会无限递归或丢节点 | `repairHierarchy()` 检测环并打断 |
| 27 | 索引排序用 `(a.parentId ? 0 : -1) - (b.parentId ? 0 : -1)` 这种无意义比较 | 每个父节点单独做顺序合并（见 02 文档第 4 节） |
| 28 | 内容指纹（checksum）**包含了时间戳**，导致每次同步都判定"有变化"，每次都上传 | 指纹只由同步相关字段算出；时间戳变化不触发上传 |
| 29 | `pushToRemote` 拿**本地树**的哈希和"上次推送的哈希"比，逻辑不成立 | 比的是"合并结果的指纹"和"云端文件的指纹"，语义明确 |
| 30 | 没有防重入（靠 UI 层的 version 计数凑），快速连点会出问题 | `SyncService` 内部有同步锁，重复调用直接报"上一次同步还没结束" |
| 31 | 云端 JSON 完全不校验，字段缺失就崩 | `parseSnapshot()` 逐字段校验：缺字段补默认值、坏记录跳过并提示、uid 重复就重新分配 |
| 32 | Gist 文件超过 1MB 会被 API 截断，旧代码直接 `JSON.parse` 截断内容 → 崩 | 检测 `truncated` 标记，改从 `raw_url` 取全文 |
| 33 | 写回浏览器时，如果先删了父文件夹，里面的书签会被连坐删掉 | `applySnapshot()` 固定六个有序步骤：**先移动、后删除** |
| 34 | 单条书签操作失败会让整个同步崩掉 | 每步都容错，失败记成提示继续走，下次同步自动纠正 |
| 35 | 冲突解法的"保留两者"用 `${id}-remote` 拼 id，可能撞车 | 用新生成的随机 uid |
| 36 | 没有测试 | 102 个用例，含**两台设备端到端同步仿真** |

## 五、架构上的变化

### 从"三层糊在一起"到"严格分层"

旧代码里，`sync-engine.ts` 同时做：读浏览器书签、调 GitHub、算合并、
写回浏览器、更新状态。这个文件 439 行，每改一处都要担心碰坏别处。

新结构按**依赖方向**分层，每层只依赖下面一层：

```
ui（界面） → background（接线） → features（功能） → platform（适配） → core（纯逻辑）
```

关键收获是 `core` 完全不依赖浏览器 API，所以同步算法**可以被测试**。

### 依赖注入：让"两台设备"能在测试里跑起来

`SyncService` 的构造函数收的是三个**接口**而不是具体实现：

```ts
new SyncService({
  adapter,   // 书签读写（真实=chrome.bookmarks，测试=内存假货）
  remote,    // 云端读写（真实=GitHub Gist，测试=内存变量）
  store,     // 本地存档（真实=IndexedDB，测试=内存对象）
  ...
})
```

于是 `tests/e2e.sync.test.ts` 能用两个假浏览器 + 一个假 Gist，
把"两台设备来回同步"完整跑一遍——**包括首次同步不重复、删除传播、
冲突中断与恢复、覆盖保护**这些真正的风险点。

### 状态所有权唯一

界面**不直接**读写书签和数据库，只发消息。规则简单到不会出错：
**后台是唯一的数据所有者，界面只负责显示和下发指令。**

同时，小状态放 `chrome.storage.local`，界面订阅它的变化自动刷新——
不需要自己写事件总线，也不会有"两个页面数据不一致"。

## 七、有意保留或未做的

保持诚实，这些是**已知的取舍**，不是遗漏：

| 项 | 说明 |
|----|------|
| Token 加密仍是"混淆级" | 密钥材料就在同一台机器上。真正起作用的是"只勾 gist 权限"。见 [07-常见问题](07-常见问题.md) 第五节 |
| GET 与 PATCH 之间有竞态窗口 | Gist API 不支持条件请求（没有 `If-Match`），两台设备在同一秒上传时后写者覆盖。窗口只有几百毫秒，且有自动备份兜底 |
| 仍只支持 Chrome / Edge | 适配器接口（`BookmarkAdapter`）已经留好，加 Firefox 只需要再写一个实现 |
| 冲突时文件夹不支持"保留两者" | "把一个文件夹变成两个"没有合理语义，界面上只给两个选项，并会说明原因 |
| 顺序冲突不打扰用户 | 只影响排序，不影响数据完整性；以远端为骨架合并 |
| 删除操作不征求确认 | 单条删除由浏览器的撤销（Ctrl+Z）兜底；只有"删除 vs 修改"的冲突才弹界面 |
| 没有下拉刷新、没有暗色主题 | 界面保持朴素，把复杂度留给真正重要的部分 |
