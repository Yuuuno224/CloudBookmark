# 02 · 同步原理：三方合并

这篇是整个项目**最核心**的一篇。看完你应该能回答：
"为什么同步不会把我的书签弄丢？两边都改了会怎样？删掉的书签是怎么传播到另一台设备的？"

---

## 1. 先说结论：为什么需要三份数据

假设你只有"本地"和"云端"两份数据，看下面这条记录：

| | 本地 | 云端 |
|---|---|---|
| 书签《GitHub》 | 有 | 没有 |

请问：应该**把本地的删掉**（因为云端删了它），还是**把云端的加上**（因为本地新增了它）？

**光看这两份数据，永远猜不出来。** 两种情况数据上一模一样。

所以必须要有第三份数据：**base —— 上次同步成功时的样子**。

| base | 本地 | 云端 | 真实的含义 | 应该做什么 |
|------|------|------|-----------|-----------|
| 有 | 有 | 没有 | 云端删掉了它 | 删除 |
| 没有 | 有 | 没有 | 本地新增了它 | 保留 |
| 有 | 没有 | 有 | 本地删掉了它 | 删除 |
| 没有 | 没有 | 有 | 云端新增了它 | 添加 |

**这就是三方合并的全部思想。** 剩下的都是细节。

base 存在本机 IndexedDB 里（键名 `snapshot:base`），每次同步成功后更新。

---

## 2. 核心概念：uid（永久身份）

比较两条记录"是不是同一条"，不能靠标题（会改名）、不能靠网址（会改址）、
更不能靠浏览器的 id（换台电脑就变了）。

所以每条书签/文件夹都会被分配一个 **uid**：一串 16 位的随机字符，例如
`k7Fq2mXp9vLdR3sT`。它的特点是：

- 在**任何设备**上，同一本书签的 uid 都一样（因为它跟着数据一起同步过去）
- 浏览器 id 变了也不影响 uid
- 两台互不通信的设备同时生成 uid 也不会撞（随机空间有 62^16 那么大）

`浏览器节点 id → uid` 的对应关系存在 IndexedDB 里（`uidmap`）。
实现见 `src/platform/uid-map.ts`。

### 根目录的 uid 是"算出来"的，不是随机生成的

浏览器的"书签栏""其他书签"这些根目录，两台不同浏览器必须能对上号。
所以根目录不用随机 uid，而是**按位置**推导：

```
Chrome 的第 0 个根目录  →  root:0   （书签栏）
Chrome 的第 1 个根目录  →  root:1   （其他书签）
Edge   的第 0 个根目录  →  root:0   （收藏夹栏）  ← 和 Chrome 对上了
Edge   的第 1 个根目录  →  root:1   （其他收藏夹）
```

因为 Chrome 和 Edge 都是 Chromium，根目录顺序一致，所以能对上号。

## 3. 合并规则总表

代码在 `src/core/merge.ts`。整体流程：**按 uid 逐条比较**。

### 3.1 一条记录只在一边存在

| base | 本地 | 云端 | 结果 |
|:----:|:----:|:----:|------|
| 无 | 有 | 无 | 用本地（本地新增） |
| 无 | 无 | 有 | 用云端（云端新增） |
| 有 | 有 | 无 | 删除（云端删了，本地没动） |
| 有 | 无 | 有 | 删除（本地删了，云端没动） |
| 有 | 无 | 无 | 删除（两边都删了） |
| 有 | 无 | **改了** | ⚠ **冲突**（本地删、云端改） |
| 有 | **改了** | 无 | ⚠ **冲突**（云端删、本地改） |

注意最后两行：凡是"一边删、一边改"，都会变成冲突问你。
**这是刻意的**——删除是不可逆的，宁可多问一句，也不能默默丢掉用户的修改。

### 3.2 两边都存在

| base | 本地 | 云端 | 结果 |
|:----:|:----:|:----:|------|
| 有 | 没动 | 改了 | 用云端 |
| 有 | 改了 | 没动 | 用本地 |
| 有 | 改了 | 改成了和本地一样 | 用哪个都一样 |
| 有 | 改了 | 改了 | **逐字段判断**（见下） |
| 无 | 有 | 有 | 身份配对后的情况（见第 5 节） |

"没动"的定义是：这一条记录的内容和 base 完全一样（比较类型、标题、网址、所在文件夹）。

### 3.3 "两边都改了"再往下拆：逐字段合并

一条书签有四个可变的字段：**类型**、**标题**、**网址**、**所在文件夹**。逐个比较：

- 两边改成一样 → 就用那个值
- 只有一边改动过这个字段 → 用改动的那个
- **两边都改了这个字段，而且改得不一样** → 记一个冲突

举个常见的例子，你在公司电脑和家里电脑上分别改了同一本书签：

| 字段 | base | 本地（公司） | 云端（家里） | 结果 |
|------|------|-------------|-------------|------|
| 标题 | `GitHub` | **`GitHub 首页`** | `GitHub` | 用本地（只有本地改了） |
| 网址 | `https://github.com` | `https://github.com` | **`https://github.com/dashboard`** | 用云端（只有云端改了） |
| 文件夹 | `开发` | `开发` | `开发` | 不变 |

**结果：标题用你的、网址用家里的，两处改动都保住了，而且不需要打扰你。**
这就是"逐字段合并"的价值——只有真正改到同一处才需要打断你。

## 4. 排序（顺序）怎么处理

排序不放到字段冲突里，而是**每个文件夹单独算**。规则从可靠到不可靠依次尝试：

1. 两边的顺序一样 → 就用它
2. 本地的顺序 = base 的顺序（说明只有云端调过顺序）→ 用云端的
3. 云端的顺序 = base 的顺序（说明只有本地调过顺序）→ 用本地的
4. 两边都调过 → 以云端为骨架，把本地独有的项插到"它在本地的前一个兄弟"后面

**顺序冲突永远不会弹给用户**，因为它不影响"有没有这条书签"，
最坏结果只是排序不完全符合某一端的期望，而且不会丢东西。

> 顺带一提：排序在代码里是用每个文件夹下的 `index` 字段表达的（0、1、2…）。

## 5. 首次同步：为什么不会把书签变成两份

这是一个非常容易踩的坑。新设备刚装上扩展时，本机**没有 base**。
它有自己的书签（比如 200 条），云端也有 200 条（其实是同一批）。
如果直接"两边取并集"，你会得到 400 条书签，而且全是重复的。

解决办法是 **身份配对（reconcile）**：既然没有历史可以依靠，就靠内容去猜。

配对规则（顺序执行，从可靠到不可靠）：

1. **书签**：网址归一化之后相同，而且**两边都只出现一次** → 认为它们是同一条
2. **文件夹**：标题相同 + 所在文件夹相同，而且唯一 → 认为它们是同一条

"归一化"指的是把 `HTTPS://GitHub.com/` 和 `https://github.com` 看成一样
（统一大小写、去掉末尾多余的斜杠），但**不动查询参数和锚点**——因为
`?q=1` 和 `?q=2` 通常是两条真的不一样的书签，不能合并。

配对成功之后，本地那条书签会**改认远端的 uid**（代码里叫 renames）。
这样一来，后面的合并就认为它们是同一条，不会各建一份。

> 刻意不做的事：如果某个网址在一边出现了两次以上，**就放弃配对**。
> 猜错会导致两条不同的书签被粘在一起，那比重复更糟。这种情况下
> 结果可能是重复的，用户可以到"数据"标签页用"重复书签清理"处理。

如果配对结果不符合你的期望，可以在设置页把"第一次同步"改成
"以本机为准覆盖云端"或"以云端为准覆盖本机"。默认是配平后合并。

## 6. 删除是如何传播的

这是老版本最严重的功能 bug（删除根本不会同步），这里说明新版本的做法。

假设设备 A 和 B 都同步过一次，base 里有《GitHub》。

```
① 你在 A 上删掉《GitHub》
   A: 本地没有 → 云端还有 → base 还有
   判定：本地删了它，云端没动  → 删除
   A 把结果上传，云端也没有《GitHub》了

② B 同步
   B: 本地还有 → 云端没有 → base 还有
   判定：云端删了它，本地没动  → 删除
   B 本地也删掉了
```

**新版本不需要"墓碑（tombstone）"机制。** 老版本想在删除时记一条"墓碑"
来防止删除丢失，但因为从来没写过墓碑，删除压根没同步过。
有了 base 之后，删除天然就是可传播的，墓碑是多余的复杂度。

### 那"删了又回来"是怎么回事？

如果 B 在同步之前自己改了《GitHub》（而不是干看着），那就变成
"一边删、一边改"→ 冲突 → 默认**保留被修改的那一份**。看起来就像"删了又回来"。

这是有意的：宁可保留，也不静默丢掉你的修改。想真正删掉的话，
在冲突界面选"确认删除"即可。

## 7. 冲突：两种，界面上的说法不一样

代码：`src/core/merge.ts` 产生冲突，`src/core/resolve.ts` 应用你的选择。

### 第一种：两边都改了同一处（`kind: 'fields'`）

界面上列出"上次同步时 / 本地现在 / 云端现在"三列，按钮有：

- **保留本地** —— 用本地那一份
- **使用远端** —— 用云端那一份
- **两者都留** —— 只在书签上提供：本地保留，另外新建一份远端的副本
  （标题会加"（远端副本）"，而文件夹不提供这个选项，因为"把一个文件夹
  变成两个"没有合理的语义）

### 第二种：一边删、一边改（`kind: 'delete-modify'`）

这种情况"保留两者"没有意义，所以只有两个按钮，而且文案会直接说清后果：

- 本地删了、云端改了 → 按钮是「**确认删除**」/「**保留远端修改**」
- 云端删了、本地改了 → 按钮是「**保留本地修改**」/「**确认删除**」

### 冲突时的状态机

```
同步 → 发现冲突 → 状态变成"等待处理"，把合并结果和冲突列表存进 IndexedDB
                 （这一步不改任何书签，你的数据完全没被动过）
   │
   ├── 你去冲突界面逐个选择 → 应用 → 执行合并 → 上传云端 → 状态回到"已同步"
   │
   └── 你点"放弃处理" → 丢掉这次的结果 → 下次同步会重新算一遍（结果一样）
```

### 一个重要的保护

如果你在冲突界面停留期间又在浏览器里改了书签，点"应用"时会**拒绝执行**，
提示"本地书签在等待处理期间又变化了"。

原因：那份合并结果是基于**当时的**本地状态算出来的。现在本地已经变了，
硬套上去会把你刚做的改动覆盖掉。刷新后重新同步一次再处理即可。

### 想完全不被打断？

设置页的"冲突策略"可以改成"自动保留本地"或"自动使用云端"。
这时同步不会暂停，冲突仍然会记进历史，但结果直接按策略定下来。

> 注意：策略**只影响"两边都改了同一处"** 这一种冲突。
> "一边删一边改"永远会来问你（除非你选了自动策略——这时默认保留被修改的一方）。

## 8. 脏数据兜底：宁可挂错地方，绝不丢数据

云端的 JSON 可能被人手改过、可能是旧版本、可能因为意外而结构错乱。
合并完以后一定会经过 `repairHierarchy()` 这一步"体检 + 修复"：

| 问题 | 处理方式 |
|------|---------|
| 某条记录的"上级文件夹"不存在（孤儿） | 挂到「其他书签」下，并给出提示 |
| 文件夹互相嵌套成环（A 是 B 的父，B 又是 A 的父） | 打断环，把其中一条提到「其他书签」 |
| `index` 重复或乱序 | 重新编号成 0、1、2… |
| uid 重复 | 重新分配一个，并给出提示 |
| 字段缺失或类型不对 | 补成合法值（例如没有 `kind` 时按有没有网址来判断） |

**原则是：宁可把一条书签挂到"其他书签"下面，也不能让它消失。**

一个典型的真实场景：云端删掉了一个文件夹，但你在本地往这个文件夹里加了新书签。
合并结果是"文件夹被删、新书签保留"→ 新书签变成了孤儿 → 自动挂到「其他书签」下，
并在同步结果里提示你"有 1 个书签的上级文件夹不存在，已临时挂到其他书签下"。

## 9. 写回浏览器的顺序（为什么不能随便调）

合并出来的结果要写回 `chrome.bookmarks`，而这个 API **没有事务**
（不能"要么全成功要么全失败"）。所以顺序非常重要：

```
1. 先创建缺失的文件夹（父目录优先，否则新建的子文件夹没地方放）
2. 再创建缺失的书签
3. 更新标题 / 网址
4. 移动换了文件夹的节点      ← 必须在删除之前！
5. 删除目标里已经没有的节点（自底向上）
6. 重新读一遍，按目标顺序调整排序
```

第 4 步排在第 5 步之前是**必须的**：如果先把父文件夹删了，
里面的书签会被连坐删掉，哪怕它们本来应该被保留。

另外每一步都是"容错"的：单条操作失败不会让整个同步崩掉，
而是记成一条提示继续往下走，下次同步会自动纠正。

代码：`src/platform/apply.ts`。

## 10. 怎么省接口次数

GitHub 免费账号每小时有 5000 次接口额度，听起来很多，但如果你
每次改书签都同步一次，也可能用完。所以：

1. **内容指纹（revision）**：内容是"同步相关字段"的哈希，**不含时间戳**。
   只有指纹真的变了才会上传。这样"打开扩展什么都没干"不会产生任何写入。
2. **变更防抖**：连续改多个书签时，等 3 秒没有新动作才同步一次。
3. **最小间隔**：两次自动同步之间至少间隔 20 秒。
4. **只读一次**：一次同步只 `GET` 一次 Gist。

反过来说，手动点"立即同步"永远不会被限制，随时可用。

## 11. 一页速查

| 我想知道… | 结论 |
|-----------|------|
| 会不会因为同步丢书签？ | 不会。删不掉的东西会挂到「其他书签」并提示 |
| 两边改了同一处会怎样？ | 暂停，让你选；或按你设置的自动策略 |
| 一边删一边改会怎样？ | 一定问你，默认保住修改（删除不可逆） |
| 删掉的书签会同步到另一台吗？ | 会。靠 base 判断，不需要墓碑 |
| 新设备第一次同步会重复吗？ | 默认不会，会按网址配对。可在设置里改策略 |
| 顺序变了会冲突吗？ | 不会，顺序单独合并，不打扰你 |
| 会白刷 GitHub 接口吗？ | 内容没变就不上传；自动同步有防抖和最小间隔 |
