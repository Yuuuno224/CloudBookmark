## 2. 按代码阅读顺序

想彻底搞懂，按这个顺序读（大约一两小时）：

```
第 1 步   src/core/types.ts
          先知道数据长什么样。整个项目都在围绕 Entry 和 Snapshot 转。

第 2 步   src/core/entries.ts
          记录级的小工具：判断"内容变了没有"、修复层级、组装成树。

第 3 步   src/core/snapshot.ts
          快照怎么变成 JSON、JSON 怎么变回快照。看懂 computeRevision（指纹）。

第 4 步   src/core/merge.ts        ★ 心脏
          三方合并。对照 02 文档里的表格读，一行一行都能对上。

第 5 步   src/platform/uid-map.ts  ★ 心脏
          浏览器书签 → 带 uid 的 Entry。看懂"身份"以后一切都通了。

第 6 步   src/platform/apply.ts    ★ 心脏
          合并结果 → 浏览器操作。注意六个步骤的先后顺序。

第 7 步   src/features/sync/service.ts  ★ 总指挥
          把上面几块串起来。重点看 #merge() 的注释分段。

第 8 步   src/background/handlers.ts
          后台提供了哪些接口。相当于后台的 API 文档。

第 9 步   src/ui/*
          界面。看不懂尖括号就先看 05 文档。
```

## 3. 每个文件一句话

### `src/core/` —— 纯逻辑，不碰浏览器

| 文件 | 一句话 |
|------|--------|
| `types.ts` | 所有数据结构的定义，以及 `AppError`（带错误码的错误类型） |
| `ids.ts` | 生成 uid、记录 id、当前时间 |
| `entries.ts` | 记录级工具：比较、排序、分组、修复层级、组装树 |
| `snapshot.ts` | 快照的序列化/解析/旧格式迁移/内容指纹/URL 归一化/首次配对 |
| `merge.ts` | 三方合并算法（含排序合并、冲突识别） |
| `resolve.ts` | 把用户在界面上的选择应用到合并结果上 |

### `src/platform/` —— 与外部世界打交道

| 文件 | 一句话 |
|------|--------|
| `bookmarks.ts` | 定义 `BookmarkAdapter` 接口 + Chrome 的实现 |

## 4. 几个"为什么这么写"

**为什么 `core` 里一个 `chrome.` 都没有？**
为了能测试。`tests/e2e.sync.test.ts` 用两个假的浏览器 + 一个假的 Gist，
在内存里把"两台设备来回同步"跑一遍，一秒内出结果。
如果核心逻辑直接调用 `chrome.bookmarks`，这条路径就测不了，
只能靠人工开浏览器点——那样的项目必然积累 bug。

**为什么 `SyncService` 的构造函数收的都是一堆接口？**
这叫"依赖注入"。生产环境传真实的 Chrome 适配器，测试环境传内存假货，
同一份业务代码跑在两种环境里。见 `src/features/sync/service.ts` 顶部的注释。

**为什么有两个地方都能读本地书签（`getLocalService` / `getRuntime`）？**
因为导出、导入、清理重复、看统计这些功能完全不需要联网，
不应该强迫用户先配 Token。所以给它们一个"远端会直接报错"的服务实例。

**为什么消息路由用 `switch` 而不是一堆 `if`？**
因为 `switch` 结尾那句 `const exhaustive: never = request` 会让 TypeScript
在"新增了请求类型但忘了处理"时直接编译报错。
