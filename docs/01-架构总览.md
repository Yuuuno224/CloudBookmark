# 01 · 架构总览

这篇回答三个问题：**这个项目由哪几块组成**、**每一块负责什么**、**点一次"同步"以后数据是怎么流动的**。

---

## 1. 浏览器扩展的三种"运行环境"

理解本项目的第一道坎，是搞清楚代码**在哪里运行**。浏览器扩展不是"一个网页"，
它同时存在好几个互相隔离的环境：

```
┌─────────────────────────────────────────────────────────────────┐
│  ① Service Worker（后台）      src/background/                   │
│     · 没有界面，不能操作网页元素                                  │
│     · 负责一切"需要一直盯着"的事：监听书签变化、定时同步、         │
│       读写 GitHub、把数据存进 IndexedDB                          │
│     · ⚠ 会被浏览器随时休眠！所以状态必须落盘，不能只放内存变量     │
├─────────────────────────────────────────────────────────────────┤
│  ② Popup（小弹窗）             src/ui/popup/                     │
│     · 点扩展图标弹出，宽 360 像素                                 │
│     · 一关就没了，不能长期保存状态                                │
├─────────────────────────────────────────────────────────────────┤
│  ③ Options（独立设置页）        src/ui/options/                   │
│     · 一个完整标签页，空间大，适合放冲突对比、数据管理             │
├─────────────────────────────────────────────────────────────────┤
│  ④ Gist（云端）                                                  │
│     · 不在你的电脑上。就是 GitHub 上的一个私有 Gist 文件          │
└─────────────────────────────────────────────────────────────────┘
```

① 和 ②③ 是两个独立的 JavaScript 运行环境，**不能直接互相调用函数**，
只能靠 `chrome.runtime.sendMessage` 传消息（就像两台电脑之间发请求）。
这就是为什么项目里会有一个 `src/platform/messaging.ts`——它定义了这批消息的格式。

> 为什么不让界面直接读写数据？
> 因为"谁拥有数据"必须唯一。如果弹窗、设置页、后台都能改书签和数据库，
> 迟早会出现"两个页面同时写、互相覆盖"的怪问题。
> 本项目的规则很简单：**后台是唯一的数据所有者，界面只负责显示和下发指令。**

## 2. 代码分层

```
                    ┌───────────────────────────────┐
   界面层            │  src/ui/                       │
   (只显示+发指令)    │   popup / options / shared     │
                    └───────────────┬───────────────┘
                                    │ chrome.runtime.sendMessage
                    ┌───────────────▼───────────────┐
   接线层            │  src/background/               │
   (注册监听、路由)   │   index.ts   入口与监听注册     │
                    │   handlers.ts 消息路由          │
                    │   scheduler.ts 定时/防抖/徽章   │
                    │   runtime.ts  组装零件          │
                    └───────────────┬───────────────┘
                                    │ 调用
                    ┌───────────────▼───────────────┐
   功能层            │  src/features/                 │
   (业务编排)        │   sync/service.ts  ← 同步总指挥 │
                    │   gist/*  远端读写              │
                    │   settings / token / history   │
                    └───────────────┬───────────────┘
                                    │ 使用
        ┌───────────────────────────┼───────────────────────────┐
        │                           │                           │
┌───────▼────────┐        ┌─────────▼─────────┐       ┌─────────▼─────────┐
│  src/core/     │        │  src/platform/    │       │  浏览器 / GitHub   │
│  纯逻辑         │        │  外部世界适配      │       │  (真实环境)        │
│  类型/合并算法  │        │  书签API/存储/消息 │       │                   │
│  ← 可单元测试   │        │                   │       │                   │
└────────────────┘        └───────────────────┘       └───────────────────┘
```

各层的一句话职责：

| 目录 | 职责 | 有什么特点 |
|------|------|-----------|
| `src/core/` | 定义数据长什么样、算怎么合并 | **纯函数**，不碰浏览器 API，所以能用单元测试完整覆盖 |
| `src/platform/` | 把浏览器 API 包装成"好用的接口" | 唯一直接调用 `chrome.*` 的地方 |
| `src/features/` | 把多个能力编排成一个功能 | 例如"同步"= 读书签 + 读云端 + 合并 + 写回 |
| `src/background/` | 接线：注册监听、路由消息 | 代码很薄，但**必须写在文件顶层**（原因见下） |
| `src/ui/` | 界面 | 只发指令、只读 `chrome.storage` 里的状态 |

### 为什么要把 `core` 单独拆出来？

因为同步算法最容易出错，而它出错会**直接删掉用户的书签**。
把它写成不依赖浏览器的纯函数以后，就可以在测试里造两台"假设备"，
让它们来回同步几百次，一秒跑完——见 `tests/e2e.sync.test.ts`。
这是本项目质量的主要保障。

## 3. 一次"合并同步"的完整数据流

假设你在弹窗里点了"立即同步"：

```
① 弹窗：sendMessage({ type: 'sync:run', mode: 'merge' })
        │
② 后台 handlers.ts 收到消息 → 调 scheduler.runSync()
        │  · 检查是否已有同步在跑（避免连点两下把数据搅乱）
        │  · 打开"变更记录静默窗口"（否则我们自己的写入会被记成"你改的"）
        │
③ runtime.ts 组装好 SyncService（书签适配器 + 远端 + 存档）
        │
④ service.ts 开始干活：
        │
        │  (a) 读本地书签
        │      chrome.bookmarks.getTree() → 转成统一的 Entry 列表
        │      每个浏览器节点绑一个稳定 uid（绑定关系存 IndexedDB）
        │      ⚠ 读完立刻保存 uid 表，否则下次读身份又变了
        │
        │  (b) 读云端
        │      GET /gists/:id → 解析 cloudbookmark.json
        │      如果是旧格式会自动迁移
        │
        │  (c) 读 base（上次同步完成时的快照，存在 IndexedDB）
        │
        │  (d) 三方合并 threeWayMerge(base, local, remote)
        │      → 得到合并结果 + 冲突列表
        │
        │  (e) 有冲突且策略是"问我"？
        │      是 → 把结果存起来，状态改成"等待处理"，**到此为止**（不改任何书签）
        │      否 → 继续
        │
        │  (f) 备份 + 写回浏览器
        │      先建文件夹 → 再建书签 → 改标题 → 移动 → 删除 → 排序
        │      （顺序很重要，见 02 文档的说明）
        │
        │  (g) 内容有变化才 PATCH 云端的 Gist
        │
        │  (h) 把合并结果存成新的 base，状态改回"已同步"
        │
⑤ 弹窗通过 chrome.storage.onChanged 自动刷新显示
```

这里有一个值得记住的设计：**界面从不主动"拉取"状态，只是"照镜子"。**
后台把状态写进 `chrome.storage.local`，界面订阅 `onChanged`。
后台一改，界面自动重画，两边永远不会不一致。

## 4. 数据放在哪

| 数据 | 存放位置 | 为什么 |
|------|---------|--------|
| 设置、同步状态、设备 ID、加密后的 Token | `chrome.storage.local` | 小、而且界面需要**实时**看到变化（有 `onChanged` 事件） |
| base 快照、uid 绑定表、待处理冲突、备份 | **IndexedDB** | 大（书签上千条时几百 KB 到几 MB），`chrome.storage` 装不下也写得慢 |
| 变更记录、同步历史 | IndexedDB | 条数多 |
| 书签数据本体（云端） | GitHub 私有 Gist | 这就是本项目的卖点：数据在你自己账号下 |

详细字段见 [03-数据格式说明](03-数据格式说明.md)。

## 5. 三个必须知道的"坑"（都已在代码里处理）

### 坑 1：Service Worker 会被休眠

浏览器觉得后台闲着就把它杀掉，有事件时重新执行一遍入口文件。后果：

- 所有 `chrome.xxx.addListener(...)` **必须写在模块顶层**。
  如果写在 `async function init()` 里，脚本被重启时监听器根本没装上，
  表现就是"功能时好时坏"。
- 不能只把状态放在内存变量里，必须落盘。

代码对应：`src/background/index.ts`（全部监听器都在顶层）。

### 坑 2：自己写书签也会触发书签事件

同步时我们把合并结果写回浏览器，这会触发几百个 `onCreated` / `onRemoved`。
如果不处理，变更记录会被自己的操作刷屏，还会误以为"用户改了东西"要再同步一次。

代码对应：`src/features/history/change-tracker.ts` 里的**静默窗口**。
写入前打开，写入后再延长几秒（事件是异步派发的，关太早会漏掉尾巴）。

### 坑 3：浏览器的书签 id 不是永久身份

`chrome.bookmarks` 给的 id（就是那个 `"42"`）**换台电脑就会变**。
如果拿它当身份，两台设备就会认不出"这其实是同一本书签"，
结果就是重复、以及"删了又回来"。原版最大的 bug 就在这里。

代码对应：`src/platform/uid-map.ts`。我们给每个书签分配一个永久的 `uid`，
把 `浏览器id ↔ uid` 的对应关系持久化下来。

## 7. 两个"附加题"是怎么实现的

### 7.1 深色模式：只换变量，不换组件

界面里**一个 `dark:` 前缀都没有**。做法是：

1. 所有颜色写成一个 CSS 变量，浅色一套、深色一套（`src/ui/styles.css`）
2. Tailwind 里把这些变量注册成**语义化颜色名**
   （`bg-surface`、`text-ink`、`border-line`…，见 `tailwind.config.js`）
3. 切换主题 = 在 `<html>` 上换一个类名（`.dark` / `.light` / 都不加=跟随系统）

```
组件里写 bg-surface
        ↓
Tailwind 生成 background: var(--cb-surface)
        ↓
:root.dark { --cb-surface: #1e293b }   ← 只改这一处
```

好处有三个：换配色只改一个文件；组件代码里不会出现"这个颜色长什么样"；
状态相关的颜色统一用五个语义色调（`default/info/warn/danger/success`），
`format.ts`（算状态）和 `components.tsx`（画颜色）之间不需要翻译层。

有个小细节值得一看：`index.tsx` 在 `render()` 之前会先读一次
`localStorage` 里缓存的明暗，先把类名套上。因为 `chrome.storage.local`
是异步的，等它读完再套会看到一下白屏闪烁。

### 7.2 用 GitHub 账号授权：为什么必须用"设备流程"

常见的"点按钮 → 跳到 GitHub → 授权后跳回来"在**没有后端服务器**的
浏览器扩展里走不通：拿到的临时 code 需要用 `client_secret` 才能换成 token，
而扩展的代码是公开的，任何密钥都藏不住。

GitHub 的**设备流程**（Device Flow）是专门为命令行工具这类无后端客户端设计的：

```
① 扩展 POST https://github.com/login/device/code   （只需要 client_id）
   ← 拿到一个长码（自己用）和一个 8 位短码（给用户看）

② 用户打开 https://github.com/login/device，填短码，点同意

③ 扩展每隔几秒 POST https://github.com/login/oauth/access_token
   ← 用户还没同意就返回 authorization_pending，同意了就返回 access_token
```

**全程不需要 client_secret**，所以纯前端扩展也能安全地用。

还有两个实现上的讲究：

- **轮询状态存在 `chrome.storage.local` 里，而不是内存里。**
  后台 Service Worker 随时会被浏览器回收，如果在那里写一个跑十几分钟的
  循环，被回收就前功尽弃。所以拆成"申请设备码"和"问一次好了没"两个动作，
  由界面按节奏调用，后台被回收也不影响。
- **请求头只能用 CORS 安全列表里的字段**（`Accept` 和
  `Content-Type: application/x-www-form-urlencoded`）。GitHub 明确说明
  设备授权端点**不支持 CORS 预检**，加一个自定义头就会让请求直接失败。
